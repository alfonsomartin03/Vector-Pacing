# Architecture

Vector Pacing is a static single-page app. Every calculation runs in the browser; the site needs only
a static file host such as GitHub Pages.

```
frontend/src/App.tsx, components/, drafting/      React UI (Recharts)
   │  runPacing / runDrafting / loadDemoCourse / loadCourseFile
   ▼
frontend/src/engine/client.ts     main thread: GPX parsing (DOMParser), one Web Worker per run,
   │                              cancel = terminate the worker
   ▼  postMessage (structured clone)
frontend/src/engine/worker.ts → handle.ts
   ├── pacing.ts     response shaping (same shapes as the former /api/simulate and /api/optimize)
   │   ├── simulate.ts   physics (closed-form cubic), CP/W′ balance, coasting / speed limit / stall
   │   └── optimize.ts   terrain segments + bounded heuristic + independent verification
   ├── drafting.ts   rider-position import, course projection, synchronisation, zone test,
   │                 interval classification, dismissed encounters
   └── fit.ts        FIT reader (positions) and .fit rides → rider-position document
frontend/src/engine/course.ts     GPX → resampled course (distance, elevation, grade)
frontend/src/data/                demo_course.gpx, drafting_demo.json (lazy-loaded chunks)
```

* **No backend.** Nothing is fetched except the site's own static assets. The demo course and drafting
  scenario are bundled as lazy chunks. Uploaded GPX, JSON and FIT files are read locally with
  `File.text()` / `File.arrayBuffer()`; a course `.gpx` for the drafting check is parsed on the main
  thread, because workers have no `DOMParser`.
* **Web Worker.** Pacing and drafting runs happen in a module worker, so the page stays responsive.
  Each run starts a fresh worker, which is terminated when the run finishes, is superseded or is
  cancelled. Where `Worker` is unavailable (the Vitest/jsdom test environment), the same handler runs
  in-thread.
* **Base path.** `VITE_BASE_PATH` sets Vite's `base`. Built asset URLs, the worker URL
  (`new URL('./worker.ts', import.meta.url)`) and the worker's lazy chunk all resolve under it, so the
  app works at `/Vector-Pacing/` on GitHub Pages and at `/` locally.
* **Response shapes.** The engine returns the same JSON shapes the Python API returned
  (`src/types.ts`, `src/drafting/types.ts`, minus the removed power screen), so the UI components,
  charts and export code are unchanged in structure.
* **Drafting is independent.** `drafting.ts` imports nothing from the pacing modules. The two tabs
  share only the shell, styles and download helper.
* **Frontend state.** Each result stores a key derived from the course/scenario identity plus the
  validated settings. When current inputs differ, results are dimmed, a banner says they are out of
  date and export is disabled.
* **Determinism.** Identical inputs produce identical outputs. The bundled data was generated by
  `backend/scripts/generate_demo_course.py` and `backend/scripts/generate_drafting_demo.py`.

## Python reference

`backend/vector_pacing` is the original FastAPI + NumPy/SciPy implementation. The TypeScript engine
is a port of `course.py`, `physics.py`, `athlete.py`, `simulate.py`, the GPS part of `drafting.py` and
the position part of `fit.py`/`review.py`, with the same constants and rules. Tests in `frontend/src/test/engine.test.ts` check the port against
values produced by the Python code. The optimizer is not a port: SciPy's SLSQP was replaced by the
heuristic described in [MODEL.md §6](MODEL.md#6-optimizer--frontendsrcengineoptimizets). The
reference also contains features the browser demo dropped: the RaceGuard power screen (and FIT power
decoding) and the `vector-pacing-review` command.
