# Architecture

```
frontend/ (React + TypeScript + Recharts, Vite)
   │  JSON over HTTP (/api/*), stateless
   ▼
backend/vector_pacing/api.py        FastAPI transport: validation (pydantic), error mapping, static files
   │
   ├── course.py    GPX parsing → resampled Course (distance, elevation, grade)
   ├── physics.py   power ↔ speed (closed-form cubic, vectorised)
   ├── athlete.py   CP / W′ balance
   ├── simulate.py  Simulator: rules for coasting, speed limit, stall; feasibility
   └── optimize.py  terrain segments + SLSQP + verification

backend/vector_pacing/drafting_api.py   /api/drafting/* router (separate from pacing)
   └── drafting.py  rider-position import, course projection, synchronisation,
                    zone test, interval classification, dismissed encounters
```

* **Drafting is independent.** `drafting.py` imports nothing from the pacing modules and vice
  versa. The two tabs in the UI share only the shell, styles and download helper.

* **Domain vs transport.** `course`, `physics`, `athlete`, `simulate` and `optimize` have no web
  dependencies and are tested directly. `api.py` only maps HTTP ↔ domain objects.
* **Stateless API.** No database or sessions. Requests carry the course as `{"kind":"demo"}` or
  `{"kind":"gpx","gpx_text":...}`; the backend re-parses each time (fast, deterministic).
* **Endpoints:** `GET /api/health`, `GET /api/defaults`, `GET /api/courses/demo`,
  `POST /api/courses/parse` (multipart), `POST /api/simulate`, `POST /api/optimize`,
  `GET /api/drafting/presets`, `POST /api/drafting/analyze` (scenario `{"kind":"demo"}` or
  `{"kind":"upload","document":{...}}` plus settings).
  Interactive docs at `/docs` when the server runs.
* **Errors.** Invalid input → 422 `{"detail": "...", "kind": "validation_error"}`; bad course →
  `course_error`; physics solver failure → `simulation_error`; invalid rider-position document →
  `scenario_error`. Messages are user-facing.
* **Serving.** In development Vite (:5173) proxies `/api` to uvicorn (:8000). For the demo,
  `make serve` builds the UI and FastAPI serves `frontend/dist` and the API from one process on :8000.
* **Frontend state.** Each result stores a key derived from the course hash + validated settings. When
  current inputs differ, results are dimmed, a banner says they are out of date, and export is disabled.
  In-flight requests are aborted when superseded, cancelled, or on "Start over".
* **Determinism.** The demo course is a committed GPX generated by
  `backend/scripts/generate_demo_course.py` (no randomness, no network). The drafting scenario is a
  committed JSON generated by `backend/scripts/generate_drafting_demo.py` (fixed random seed). Identical inputs produce
  identical outputs.
